## Code structure (owner's request, 2026-10-27)

Keep functions short and simple; the owner reviews against this. Lua has no looser standard than other languages, so the usual rules apply.

- A public function reads as an outline: a few lines that call small private functions, one per step. If a function has numbered or commented sections, each section is a function.
- Rough limits, checked with a size and complexity count before handing work over: about 25 lines per function and cyclomatic complexity (1 + each `if`, `elseif`, `for`, `while`, `and`, `or`) of 8 or less. Going over needs a reason, stated in the handover. A long function with no branching (such as building a GUI) is the mildest case, but still prefer splitting it by what it builds.
- Private helpers are `local function`s defined ABOVE their callers in the same file (Lua needs a name defined before it is used). State shared between helpers goes in one small table that is passed along (see the `index` in `spec/support/blueprint_validator.lua` and `blueprint` in `scripts/layout.lua`), not in file-level variables that change.
- Splitting must not change behaviour. For a refactor, compare old and new code on many inputs (a differential run: same inputs through both versions, diff the printed results) in addition to the tests, and mutation-check the result.
- Types and names (owner's code style preferences, 2026-11-06; apply them to everything new):
  - **Annotate with the named type, not a subset of its cases.** A value that is one of a named type's cases is annotated with that type (`bpgen.ChainReason`), not with the few cases a function happens to return (`"ambiguous"|"unsupported"`). Give a set of string cases a named alias (`bpgen.PlanReason`) rather than writing it out in several places.
  - **No arrays of inline multi-field objects.** Do not write `{name: string, production: bpgen.Production}[]`; give the pair a named class (`bpgen.MadeIngredient`). Do not add a field to an unrelated type only to avoid such a pair, and do not swap the array for a dictionary when the code counts or orders the entries.
  - **Name a type, function or variable for the thing, with a noun** (`Production`, `Candidate`, `PlannedStage`), not with the `-ing` form of a verb (`Making`). A gerund names an activity or a service (`Logging`, `Routing`); a record is a thing. Agents that do work take `-er` (`Builder`, `planner`).
  - **Where a type is declared.** `scripts/types.lua` holds the types of values passed between modules: a module's arguments and results and the types they are made of, including parent types (`Plan`, `StageRequest`, `Shape`, `Production`, `ChainReason`, `Entity` and its parent `NewEntity`). A type for values only one module makes and uses stays in that module, next to the code (`Builder`, `Geometry`, `Job`, `Candidate`, `MadeIngredient`, `StageContext`, `MachineRates`, `EnergySource`). A module's own table type (`Config`) stays in its module. Types that only the test support code uses stay in `spec/support/`.
- No linter is installed in the assistant's environment (no `luacheck`). The owner can run `luacheck` with its `max_cyclomatic_complexity` and `max_code_line_length` options on their own machine if they want it enforced automatically.

## Test style (owner's rule, 2026-10-26; enforced on every commit; moved to busted 2026-10-28)

Tests run with [busted](https://lunarmodules.github.io/busted/) (`describe` / `it`, luassert assertions), chosen by the owner in place of a hand-rolled framework. Every test is written so it reads as plain English: given some setup, when one thing is called, then something is true. The owner reviews each commit against this.

1. **One `it` = one behaviour, named as a requirement a player of the mod would state** (owner's pattern, 2026-11-05): "{verb} {behavior} when {use case}", with whatever natural verb fits (`allows`, `refuses`, `needs`, `reports`; "does not ..." for what must not happen), and "when" only where it reads well. The name says the use case, not the exact setup: `it("allows the rate when it is within the limits of two output lanes", ...)`, not "allows 800 items a minute with 8 machines, because the two output lanes each carry 8 x 50.4". The numbers belong in the test body, where the setup and the arithmetic comment show them. A name has no numbers unless the number is the use case itself (two ingredients, three inserters) or a loop makes the name unique, as in the validator sweeps over machine counts. `describe` names the module or the area.
2. **The shape inside the function is setup, then one call, then assertions, separated by blank lines.** Do NOT write `-- given`, `-- when` or `-- then` comments; the layout alone must make it obvious. The call under test is a single statement, and its result goes in a local.
3. **Assertions are luassert's, which read like English:** `assert.are.equal(2, plan.machines)`, `assert.are.same({...}, tiles)` (deep), `assert.is_nil(x)`, `assert.near(expected, actual, tolerance)`, `assert.has_error(fn)`, `assert.matches(text, message, 1, true)`. ARGUMENT ORDER: EXPECTED FIRST, then the actual value (the reverse of what Java/JUnit people expect: `assert.are.equal(expected, actual)`). Custom assertions live in `spec/support/assertions.lua` (today: `has_item_containing(text, list)`, plain-text match), are loaded by `spec/helper.lua`, and have their own specs in `spec/assertions_spec.lua`. Add an assertion there instead of writing a loop or a boolean expression inside a test.
4. **Everything the expectation depends on appears inside the `it`.** A reader must be able to work out the expected value from that one function alone: write the recipe time, belt speed, coordinates and so on in the test (or as a clearly named local there), and show the arithmetic that gives the expected number in a short trailing comment (`-- 3 x 18.75`). It is fine, and expected, that this is not DRY.
4a. **Which game prototypes exist is part of the given.** `fake_prototypes{...}` starts with NO recipes; a test lists the recipe it needs with `a_recipe{energy, ingredients, products}` (all three required, plus `category` when it is not made by hand or in an assembler: `"smelting"` for a furnace recipe, which `scripts/config.lua` maps to the stone furnace; `categories = {...}` for a recipe with several) and passes any speed it depends on. The generator finds recipes by the items they make (`prototypes.get_recipe_filtered`, faked by `fake_prototypes`), so a test that needs an intermediate item lists its recipe as well, and an item with no recipe in the fake is a raw item (like an ore). Buildings exist by default; a test that needs one missing or odd says so (`missing_entities`, `furnace_speed = false`, `belt_speed = false`, `inserter_rotation_speed = false`). Other crafting machines are listed with `machines = {["assembling-machine-1"] = a_machine{crafting_speed = 0.5, size = 3}}`; a test whose numbers depend on the inserter speed passes `inserter_rotation_speed` itself. Never change the returned table afterwards.
4b. **Test each use case once, not once per item.** Iron plate, copper plate and stone brick are the same use case; the cases are shapes of recipe (one ingredient to one product, two of one ingredient to one product, one ingredient to two products) and the generator's decisions. The item names in a test are only labels that `scripts/config.lua` happens to support.
4c. **Do not keep a test that only repeats another with fewer or different items** (owner's pattern, 2026-11-06). If two tests check the same behaviour and differ only in how many ingredients, machines or steps they use, or in the numbers, the simpler one is redundant: delete it and keep the one whose name states the behaviour (e.g. "gives one step when every ingredient is raw" next to "gives one step when the recipe has several raw ingredients"; "builds more furnaces when the assemblers need more plates" next to a test that already derives the furnace count from the assemblers). Two tests stay when they reach different code or report different results (an ambiguous item versus an ambiguous ingredient). To check, delete the test and rerun the mutation list: if no mutant newly survives, it was redundant.
4c-1. **How redundancy is measured (owner's definition, 2026-11-07).** Many tests failing on one mutation is fine. A test is redundant when the only mutations it catches are ones that another test also catches alone, that is, when a group of two or more tests together catches exactly one mutation and nothing else. To find them, record for each mutation WHICH tests fail (not only whether one does), then list the mutations whose only catchers are 2+ tests that catch nothing else. The 2026-11-07 run (235 mutations) found 8 such groups; the owner chose to keep every test for now, so these are known and accepted, not bugs: chain_spec/generator_spec pairs for three made ingredients and for a mixed made and raw step (the generator test checks the message reaches the player), two blocks_spec trail tests, a planner pair for a recipe with two products, two chain loop tests. Loop-generated families (a loop that makes named tests) show up as groups too and are not duplicates.

4d. **A layout test follows the items, not only the entities** (the owner's observation, 2026-11-06). A blueprint can have every entity in place and powered and still not work: a belt that runs the wrong way strands the plates, an inserter can have nothing ahead of it. Where a rule decides which way something flows, keep a small model of the flow in the test (`plate_flow_problems` in `spec/layout_spec.lua` follows the plates along the belt) and sweep it over the shapes and counts, instead of only checking coordinates.
5. **Helpers are only for setup the test does not care about** (numbering entities, filling in fake game data the test never looks at, looking an entity up). Helpers live in `spec/support/builders.lua` or as small locals at the top of the spec file. The planner takes one request table (`planner.plan{product = ..., rate_per_minute = ..., recipe = ..., machine_speed = ..., lane_items_per_minute = ..., fuel = ..., inserters = ...}` for one step, `planner.plan_chain{rate_per_minute = ..., lane_items_per_minute = ..., stages = {{product, recipe, machine_speed, fuel, inserters}, ...}}` for a chain), so every planner test names every value it depends on, including `fuel = "coal"` for a furnace-shaped test and no `fuel` for an electric one. A helper may have defaults, but a value an expectation depends on is passed explicitly by the test (`fake_prototypes{belt_speed = 0.0625}`, `a_catalog{pole_wire_reach = 7}`), never left to a default the reader cannot see.
6. **Prefer small hand-built inputs over output from other modules.** The validator specs build tiny blueprints from `belt(...)`, `furnace(...)` and friends so every coordinate is visible; they do not call the layout. Coordinates in layout code and tests are TILES (the top-left tile an entity covers, see `scripts/grid.lua`), never hand-written centre positions with `+ 0.5`.
7. **No loops over assertions.** A loop that generates separate named tests is fine (`for _, count in ipairs({...}) do it(count .. " furnaces ...", ...) end`); a loop inside one `it` hides which case failed.
8. **Every new or changed test must be shown to fail:** break the code on purpose in a scratch copy (a mutation) and confirm a test fails. The mutation list for the current suite is in `project-status.md`. Check that every mutation really applied: a mutation whose text no longer matches the code is skipped, not failed, and looks like a pass.
9. **Files:** one `spec/<thing>_spec.lua` per module under test; busted finds them by the `_spec` suffix (see `.busted`). Support code is in `spec/support/`. Run `busted` from the repo root.
10. **Busted gotchas.** (a) Busted runs each spec file in its own sandbox: a global assigned in a spec is not seen by the module under test unless it is written `_G.prototypes = ...`. `defines` is set for all specs in `spec/helper.lua`. (b) A failing luassert message prints "Expected objects to be equal. Passed in: ... Expected: ..."; remember "Passed in" is the SECOND argument.
