# Not yet seen in game

What the specs cannot show: each section lists what a feature assumes about the game, to check on the first in-game run, one section for each feature, oldest first. The specs check the logic and the rules the blueprints follow; only the game confirms that it accepts the result.

## Unverified in iteration 2 (check on the first in-game run)

1. **Inserter orientation.** `layout.lua` sets `direction = west` on both inserters, assuming an inserter's direction is the side it PICKS UP from (so they move items east). If the inserters point the wrong way in game, swap to `east` in `layout.lua` (the layout test then needs the same change). Source: memory, not the JSON.
2. **Wire format.** Each wire is stored once, on the entity it starts from, as a four-entry list (this entity's number, connector, other entity's number, connector), using `defines.wire_connector_id.pole_copper`. The JSON describes a `BlueprintWire` as "a single wire" with a source and a target, which fits one entry per wire, but the docs do not say whether `wires` should list a wire on both ends. If the poles come out unconnected in game, try listing each wire on both poles.
3. **Entity names** `stone-furnace`, `transport-belt`, `inserter`, `small-electric-pole`, `coal`: standard base names from memory. The generator checks the entities exist and reports a message if not.
4. **Small pole range.** Spacing assumes a supply area reaching 2.5 tiles and wire reach of at least 4 tiles (the farthest wire is 4 tiles). The runtime can report real values (`get_supply_area_distance`, `get_max_wire_distance` on the entity prototype); the layout does not read them yet.
5. **Runtime `belt_speed`.** The generator treats `prototypes.entity["transport-belt"].belt_speed` as the same raw value the prototype docs call `speed` (0.03125 for the standard belt). The runtime docs say only "the speed of this transport belt". To check in game: ask for a rate above the limit (for example 1000 per minute); the message must say the maximum is 450 per minute. A different number means the unit differs.
6. **Dotted `require`** (`require("scripts.generator")`) is used for the first time. It follows the 2.0 wiki tutorial and passed under busted; confirm in 2.1.
7. **Item picker filter** (`elem_filters` by name) is verified against the JSON but untested in game.
8. **Temporary cursor blueprint** (owner request 2026-10-29: the blueprint must not take an inventory slot). `control.lua` sets `player.cursor_stack_temporary = true` after `set_stack("blueprint")`. The attribute exists (read/write boolean, see `research/api-reference-2.1.23.md`), but WHEN to set it (before or after `set_stack`), and whether pasting works with it, are untested in 2.1: a 1.1.74 forum report says paste wrongly reported a pasted blueprint as not temporary (fixed by staff the next release). If the blueprint still lands in the inventory, try setting the flag before `set_stack`, or ask the owner to attach `runtime-api.json` so the docs text for the attribute can be read.
9. Whether `set_blueprint_entities` repositions entities (the `fix_positions` default is not documented); the layout keeps entities on valid tile positions either way.

## Unverified in the iron gear iteration

1. **Inserter rotation speed units.** `get_inserter_rotation_speed` exists (verified in `runtime-api.json`) but the JSON does not say the unit. The code reads it as turns per tick (0.014 x 3600 = 50.4 items a minute, which matches the basic inserter's known 0.83 swings a second, from memory). The owner's run of the 3-in, 2-out gear version on 2026-11-01 looked right, which supports it, but nobody has compared the numbers. Check by generating 100 gears a minute: the message should say 2 machines and 100.8 gears a minute, each machine with 2 input inserters and 1 output inserter.
2. **Assembling machine 1 values** (3x3, crafting speed 0.5, no fuel) and the gear recipe (2 plates, 0.5 s) are from memory; the generator reads size, speed and recipe at runtime.
3. **Pole rows layout** is unreachable from the generator since 2026-11-01; only the layout specs exercise it. It was confirmed in game with the first gear version.
4. **Two inserters in one column beside a 3x3 machine** (tile rows 0 and 1, with the pole in row 2) are assumed to work like the three the owner ran.
5. **Plates on both input lanes.** The generator relies on inserters taking from either lane of a belt (the gear wheel puts the same item on both). Not verified; the owner was offered the chance to paste the wiki text about which lane an inserter picks up from.
6. **One lane for the product.** An inserter drops on the far lane of a belt (right-hand lane when the belt points at it). Secondary source only: forum posts quoting the wiki.
7. **Two-ingredient recipes.** The planner and generator support them (one lane per ingredient, the flows added up for the inserters), but no product in `config.products` uses one, so only unit specs cover them (made-up recipes under the `iron-gear-wheel` label). Never run in game.
8. **Fluids** are handled for a step with two or more inputs (see 5ag, 5ah); `read_recipe` keeps them apart from the items, and a step that takes one anywhere else is refused.

## Unverified in the energy source iteration

1. **What `get_item_filtered` returns.** The code reads the NAMES of the returned items as the table's keys (`for name in pairs(...)`), assuming the usual `dict[string -> LuaItemPrototype]` of the `*_filtered` functions. The owner has not confirmed the return type. If it were a plain list, the keys would be numbers, the configured fuel would never be found, and every furnace would be refused with `error-fuel-mismatch` (a visible failure, not a wrong blueprint).
2. **An empty list of filters.** Not known what the game returns, so the code never calls it with no categories (a fake that returns every item stands in for the worst case).
3. **Heat and fluid machines** are refused, not handled. Other energy sources (`heat_energy_source_prototype`, `fluid_energy_source_prototype`, void) are only assumed to be absent when the two handled ones are absent.
4. **Not run in game.** Run it by generating 50 iron plates a minute: it should build as before. A furnace is refused only when its `burner_prototype` cannot burn the configured coal.

## Unverified in the chain iteration

1. **The numbers in game.** Generating 100 iron gear wheels a minute should say 11 x stone furnace making 206.25 iron plates a minute, which feed 2 x assembling machine 1 making 100.8 iron gear wheels a minute; 225 should give 24 furnaces and 5 assemblers (NOT yet seen in game: whether all 5 assemblers and the bottom furnaces get their plates), 226 should be refused with a maximum of 225. The recipe numbers (plate 3.2 s, gear 2 plates in 0.5 s) and speeds are read at runtime, the ones here are from memory of the base game.
2. **Inserters pick from either lane.** The assemblers' input inserters take plates from the lane the furnaces' output inserters fill (the far lane) and the other lane stays empty. Already listed as unverified for the gear wheel (iteration 3); now it also matters for the middle belt.
3. **The plate belt runs north (up the page) when the furnaces reach further down.** CONFIRMED BY THE OWNER IN GAME 2026-11-06 (22:27): the belts feed the inserters correctly between chain steps. Not yet checked at the largest sizes. At 100 gears a minute all 11 furnaces should feed the 2 assemblers: the lower assembler has the first pick, the upper one gets the rest and the plates of the two top furnaces. The belt model in "Belt flow" says 100%, but it does not model the timing of an inserter picking from a moving belt, nor whether the lowest furnaces stay blocked while the higher ones can keep the belt full. Check that both assemblers run at full speed after a few minutes, and that the furnaces at the bottom are working (not stuck with full output).
4. **The wire between columns.** One wire joins the first output pole of a column to the first input pole of the next (two columns apart, at most two rows apart, so under 3 tiles). The validator accepts it at its made-up reach of 7.5; the layout does not read the pole's real reach from the game (see item 4 of iteration 2).
5. **`get_recipe_filtered` at runtime.** Verified in the 2.1.24 type library (not in game): it returns a `LuaCustomTable<string, LuaRecipePrototype>` indexed by recipe name; `RecipePrototypeFilter` `has-product-item` takes `elem_filters`, a list of item filters (here `{filter = "name", name = item}`); `LuaRecipePrototype.categories` is a list of strings; an ingredient's `type` is `"item"` or `"fluid"`. Not verified: that the filter also finds recipes whose product is a random or ranged amount, and which recipes other mods (Space Age) add in a category the config names; a second recipe for the same item in `smelting` or `crafting` is refused as ambiguous, with a message that names the item.
6. **Raw means "no recipe the mod can build".** An ingredient made only in a category the config does not name (a chemical plant, say) is treated as a raw item the player supplies, with no warning, so a recipe could ask for plastic bars on the raw belt. That is intended for now (the table of products is small), but it is a place a wrong blueprint could come from once more items are added.
7. **Message format.** `generated` now takes a nested LocalisedString as its first parameter (`{"", step, step}`); Factorio's `__1__` substitution of a nested table is standard but not run in game.
8. **Copper cable (added 2026-11-06 22:27, owner request; not run in game).** One entry in `config.products`; nothing else changed. A chain whose last step makes more than it eats: 1 plate to 2 cables in 0.5 s, so an assembler (speed 0.5) is held by its output inserters to 100.8 cables a minute from 50.4 plates (1 input inserter, 2 output inserters), and the last column's output belt winds. 100 a minute should say 3 x stone furnace and 1 x assembling machine 1; 900 (24 furnaces, 9 assemblers) is allowed, 901 refused with 900. First time the winding output belt is used inside a chain, so the winding belt's own unverified items (the two-lane rule that the first inserter takes all it can, and that the second inserter's side belt side-loads the inner lane) matter here, and 900 depends on them.
9. **Maximum rate line in the window (added 2026-11-06 22:39, owner request; not run in game).** `control.lua` adds a label (`blueprint-generation-max-rate`) right under the "Rate (items per minute)" label, and fills it when the window opens and on `on_gui_elem_changed` of the item button. The text comes from `generator.max_rate_message(item)`: the number `plan_chain` names for "rate-too-high" (`planner.max_rate`), or the refusal message when the item cannot be made, or `max-rate-no-item` when the picker is cleared. `control.lua` has no specs (nothing in it can run outside the game), so the event handler and the label placement are untested. Check: opening the window shows "Max: 450" for iron plate (shortened from "Most one blueprint can make: 450 per minute" at the owner's request, 22:44: the label above already says per minute); picking iron gear wheel changes it to 225; clearing the picker shows the hint.
10. **Demand-sized earlier steps (2026-11-06 22:49, owner request; not run in game).** 1 iron gear wheel a minute should say 1 x stone furnace and 1 x assembling machine 1, the furnace making 18.75 plates and the assembler 9.375 gears (it can only get 18.75 plates). Nothing else about the layout changed. Note that the message now shows the last step making LESS than one machine can when the stage before is small; a rate that is not a multiple of a furnace's plates is rounded up in furnaces, so the real output is at least the rate asked.
11. **Inserters follow the share of work (2026-11-06 23:09, owner idea; not run in game).** A stage with ONE machine used for less than all of its speed (`load` under 1) gets only the inserters its share needs (`rates_for` in the planner: input and output separately, `ceil(load x full flow / inserter speed)`, never more than the usual count); with two or more machines the first ones run flat out and keep every inserter (the owner's picture: all machines but the last at 100%, the last partly; the belt does this by itself, since an inserter takes what reaches it first, so nothing in the planner assigns work to machines). The last machine of a larger column keeps the full inserter count too, since the columns are laid out with identical machines. The plan shows what the trimmed machine really makes. 1 cable a minute should give 1 furnace and 1 assembler with one input and one output inserter and a PLAIN output belt (no winding); 100 gears a minute is unchanged. Check in game that the single assembler at low rates works with one inserter each side.

## Unverified in the recipe tree iteration

1. **The join.** The product belt of the lower block turns east into the side of the upper block's product belt (a curve), which has a belt behind it and so stays straight and side-loads onto its near lane. The rear-plus-side case is the one the winding output belt already relies on (the owner's report of Factorio's belt rules, 2026-11-06). The wiki pages I could read (Belt_transport_system, Transport_belts, 2026-11-07) do not cover side-loading or curves, so nothing here is checked against a source. The curve keeping each lane's identity is an assumption of the tracer and not needed by the layout.
2. **The final column's inserters take both items from one belt.** Wiki (Secondary, https://wiki.factorio.com/Inserters, read 2026-11-07): from a belt perpendicular to it an inserter takes from the nearest lane first and from the far lane when the nearest is empty. The inserters are east of the belt, so cables on the east lane are the near ones.
3. **The lanes themselves.** Same page: "Inserters place the item on the furthest lane." The owner verified in game (2026-11-07) the three rules for where an inserter puts an item: far lane across a belt, inside lane on a curve, and on a belt in line with the inserter (running toward or away from it) the belt's right-hand lane. The tracer models them; an inserter dropping onto a curve is no longer reported as a problem. The in-line rule is not used by any layout yet; it will matter with underground belts and splitters.
4. **Raw belts fed from the west.** The first tile of a belt of raw items has nothing behind it; a belt that the player brings from the west turns it into a curve, which keeps the ore and the fuel on the lanes the player chose. Not run.
5. **The maximum.** 150 circuits a minute needs 6 circuit assemblers, 5 cable assemblers and 20 furnaces; whether every circuit assembler gets its share when the cable lane is full (the first inserters have the first pick) is not known.
6. **The line of poles** beside each block and the wires between blocks: the validator accepts them (reach 7.5, supply 2.5, the numbers are not read from the game).
7. **Two furnace columns for the same ore** (an offshore pump's pipes and gears) each take a belt of their own. Not built as a product yet.
