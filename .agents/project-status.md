## Goal

A Factorio 2.1 mod where the player gives only an item to produce and a rate of output, and gets a pastable blueprint that carries raw materials (ores and so on) to machines (furnaces, assemblers) to produce the final product.

## What exists

- `info.json`, `LICENSE`, `.gitignore`, and the shortcut icons in `graphics/` (the owner will replace the icons later; `data.lua` assumes the same file names, `icon_size = 56`, `small_icon_size = 24`).
- `data.lua`: the shortcut prototype `blueprint-generation-open` (`action = "lua"`).
- `control.lua`: only registers the four events, which `scripts/gui.lua` handles (moved there 2026-11-08, see below). The window works like this: a shortcut opens or closes a window (item picker filtered to supported products and starting on `config.default_product`, iron plate (owner request 2026-10-29; set with `item_button.elem_value` after `add`, NOT verified in game, and `elem_value` as an `add` field is not in the API notes), rate field in items per minute, Close and Generate buttons). Generate calls `generator.generate`, then puts the blueprint on the cursor. The GUI is stateless (values are read from the window's elements by name), so there is no `storage`.
- `scripts/config.lua`: every hardcoded choice: the first-tier belt, inserter and pole names; `products`, the set of items a player may ask for (a set of names, not a recipe table); and `machines`, the machine and the fuel (if it burns one) for each recipe CATEGORY (`smelting`: stone furnace and coal; `crafting`: assembling machine 1). Recipes are not stored here; they come from the game (see "Chains" under Decisions). Numbers that the game already knows about those entities are NOT stored here (see Decisions).
- `scripts/planner.lua`: pure maths (small private helpers for each step, and `plan` is an outline of them). `planner.plan(request)` takes ONE table (`bpgen.PlanRequest`: product, rate, recipe, machine speed, lane capacity, optional fuel, optional inserter limits) instead of seven positional arguments, two of them plain numbers side by side that are easy to swap. It decides the machine count (float-safe rounding), how the input items sit on the two belt lanes, the inserters per side and, when inserters limit a machine, how much slower it runs. Also `lane_items_per_minute(belt_speed)` and `inserter_items_per_minute(rotation_speed)`. Since 2026-11-06 `planner.plan_chain(request)` (`bpgen.ChainRequest`: rate, lane capacity and a list of `bpgen.StageRequest`s, from the step fed raw items to the last) plans a whole chain and returns one plan per step; `planner.plan` is a wrapper that plans a chain of one.
- `scripts/layout.lua`: pure, machine count in, blueprint entities out (see "Layout" below). Written in tile coordinates. Since 2026-11-04 the steps share one `Builder` table (entities, geometry, names, machine count, poles) and are its methods; see "Passing state around" below. Since 2026-11-06 `layout.build_chain(stages, names)` lays out a row of columns (one `Builder` each, all adding to one entity list) and `layout.build` is a chain of one.
- `scripts/chain.lua`: pure. `chain.resolve(item, lookup)` follows a recipe back to the raw items and returns the steps, first step first, or a refusal reason and the item it is about (see "Chains" under Decisions). It knows nothing of the game: `lookup(item)` says how an item is made.
- `scripts/grid.lua`: pure, converts between a TILE (the top-left tile an entity covers, whole numbers, y grows down) and a POSITION (the entity's centre, which Factorio blueprints use): `grid.position(tile_x, tile_y, width, height)` and `grid.top_left_tile(position, width, height)`; sizes default to 1x1. The only place the "+ half the size" lives (owner request 2026-10-27). The validator deliberately does NOT use it, so a mistake in `grid` cannot hide behind the same mistake in the checker.
- `scripts/generator.lua`: the only module that reads `prototypes`: recipes (found by the item they make, `get_recipe_filtered`), machines (speed, size, energy source, fuels), belt speed, inserter rotation speed. It builds the `lookup` that `chain.resolve` uses, then plain tables and numbers for the planner and layout, and hands the facts for the messages to `scripts/messages.lua` (the raw items and the fuel a blueprint uses, a minute, are worked out here by `add_demand`).
- `locale/en/blueprint-generation.cfg`: all texts in a `[blueprint-generation]` section.
- `scripts/messages.lua`: all the wording (owner request 2026-11-08, so that review can look at the words apart from the features). Every refusal, the line under the rate field, the message after a blueprint is made, the captions of the window and the text of the blueprint's description. It only picks the locale key and the values: the modules that decide pass the facts in. `spec/messages_spec.lua` checks that every key it uses is in the locale file with as many values as places in the text, that no key of the locale file is unused, and the few things it works out (number formatting, the plain name of an unknown item, the comma list).
- `scripts/gui.lua`: the window: building it, reading what was entered, putting the blueprint on the cursor, and the four handlers `control.lua` registers (`on_shortcut`, `on_click`, `on_elem_changed`, `on_closed`). Not covered by tests, like the old `control.lua`.
- `spec/`: the test suite, run with busted outside the game (see "Testing"). `<thing>_spec.lua` files hold the tests; `helper.lua` (fake `defines`, loads the custom assertions), `support/assertions.lua` (custom luassert assertion), `support/builders.lua` (setup helpers) are the toolkit. `.busted` in the repo root is busted's config.
- `spec/support/blueprint_validator.lua`: layout-independent sanity checks for any list of blueprint entities (see "Testing"). Test tooling only; the game never loads it.

- Recipe trees (2026-11-07), see `recipe-tree-plan.md`: `scripts/blocks.lua` (`blocks.build(root, names)`: two blocks stacked, the final column beside the lower one, a line of poles beside each block's product belt), `layout.chain_block` and `layout.connect_poles`, `planner.plan_tree` and `planner.max_tree_rate`, `chain.resolve` giving a tree, `StageLayout.suppliers`. Test tools: `spec/support/belt_tracer.lua` (follows the items through belts lane by lane, with `spec/belt_tracer_spec.lua`) and `spec/blocks_spec.lua`.

## Decisions

- The mod is Lua, written from scratch on `llm-main`. `.agents/` is tracked in git.
- Input is a GUI opened from a shortcut-bar button. Output is a blueprint on the cursor.
- "Resource" means the ITEM TO PRODUCE (for example iron plate). The rate is in items per minute (assumption, confirm with the owner).
- Input belt lanes (owner, 2026-11-01): the input belt has two lanes, and what goes on it is the recipe's ingredients plus the fuel, if the machine burns one. One item fills both lanes; two items get a lane each (an ingredient and a fuel, or two ingredients); more are refused as `unsupported-recipe`. The player decides which lane holds which item (the message names the items). The product always rides on ONE lane of the output belt. A recipe must make exactly one product, or the extra product would clog the machine.
- One column only: a rate that needs more machines than the belt lanes can serve (24 furnaces, 450 plates a minute, for plates) is refused with a message that names the maximum, instead of building several columns. Several columns is a candidate later iteration.
- Inserters are the electric `inserter`, and the blueprint INCLUDES `small-electric-pole`s with copper wires between them; the player connects the poles to their grid. History: the owner first answered "no poles" (2026-10-25), then changed their mind later that day and asked for the poles to be coded in. Burner inserters were rejected (their output side would run out of fuel).
- Numbers that belong to a hardcoded entity are read from the game at runtime instead of stored in `config` (owner, 2026-10-26). Done so far: the belt lane capacity, computed from the belt's `belt_speed` (`speed x 4 items per lane per tile x 60 ticks x 60 seconds`; 450 per minute for the standard belt), alongside the furnace crafting speed and the recipe that were already read. Candidates for later, not done yet: the pole's supply area and wire reach (the layout still assumes 2.5 and 4 tiles), the furnace's size (`tile_width`, `tile_height`; the layout assumes 2x2), and the inserters' pickup and drop positions (which would also settle the direction question).
- Testing scaffolding (owner, 2026-10-26): build generic test tooling now, but do NOT build a general production-chain model yet; generalize from the second or third real example (steel plate is the first true chain). Unit tests use made-up numbers on purpose, so they hold whatever the game numbers are; no fixtures from real `data.raw`. The blueprint validator deliberately does NOT check belt paths (later layouts may bend belts to save space) or item flow (a game-specific quirk).
- Lanes and inserters (owner, 2026-11-01). The owner's requirements, in priority order: (1) poles reach everything that needs power; (2) minimize the number of machines; (3) minimize the length of the machine column (do not space the machines out); (4) maximize the rate one blueprint allows. Given only basic poles and no underground belts, splitters or long inserters, the owner's solution is: two lanes for the input items (see "Input belt lanes"), one product, and up to `size - 1` inserters on each side of a machine (`layout.max_input_inserters`: 1 for a 2x2, 2 for a 3x3), which leaves one tile beside every machine free for a pole. History: on 2026-10-31 the owner chose several inserters per machine (3 in, 2 out for gears, with pole rows; confirmed working in game on 2026-11-01); an intermediate "one inserter per side" version was offered and replaced by this design the same day.
- How the planner uses the inserter limit: each side gets as many inserters as the machine needs, up to the limit. When the limit is below what a machine could use at full speed, the machine runs slower (every flow shrinks by `max inserters on the busiest side x inserter items a minute / busiest side`) and everything is sized for that: with two basic inserters (50.4 items a minute each) a gear machine can take 100.8 of the 120 plates it could eat, so it makes 50.4 gears, not 60. Resulting numbers (belt lane 450): gears need 2 input and 1 output inserter per machine, at most 8 machines, 403.2 gears a minute; furnaces are unchanged. `inserter_items_per_minute(rotation_speed)` is `rotation_speed x 60 x 60`; it ignores stack bonuses and belt movement.
- Winding output belt (owner, 2026-11-02): two output inserters can fill both output lanes if the output belt is 2 tiles from the machine side and follows `DDLDRDDLDR...`: inserter A is left of the `D` between `L` and `R` (drops on the far, east lane), inserter B is left of the next `D`, dropping onto an `R` stub that side-loads the inner (west) lane of the main belt. Output inserter limit is `min(2, size - 1)` (`layout.max_output_inserters`); the input limit stays `size - 1` (`layout.max_input_inserters`); both replaced `max_inserters_per_side`. Built only for a 3x3 machine with exactly 2 output inserters in packed (free-tile pole) mode (`winds_output` in `layout.lua`); the belt then needs one more column (inner column `3+size`, outer `4+size`) and six tiles per machine. A single output inserter keeps the straight belt, so gears (1 output inserter) still use one lane; alternating the inserter rows is an optional follow-up. The planner's per-lane rule with 2 output inserters is CONSERVATIVE and UNVERIFIED in game: machines <= floor(lane / inserter items a minute), because the first inserter takes all it can. Example: a doubling recipe (1 plate -> 2 items, 0.5 s, speed 0.5) allows 806.4 a minute instead of 403.2. The validator does not check belt paths; a throwaway trace script confirmed the path and one side-load per machine. Correction (owner, 2026-11-06 22:33, from Factorio's belt rules): the outer belt starts one row ABOVE the first machine's top with an empty belt running south, so the first stub side-loads a straight belt instead of bending it into a curve (without it the first inserter's lane does not work). The earlier sentence "the first stub bends into the outer tile; the lane stays the same" was wrong. That tile sits in row -1 for a single column with no pole rows (blueprint positions are relative, so nothing else moves), and one row above the shared start row in a chain. Not run in game by me.
- Energy source of a machine (owner, 2026-11-03). Machine facts are read from the game, not hardcoded; which machine makes an item stays in `config` (by recipe category in `config.machines` since 2026-11-06) until the owner's research feature (not decided). The generator reads the machine prototype: `electric_energy_source_prototype` present means electric, `burner_prototype` present means burner (the two are mutually exclusive, and each is nil when the machine does not use it); `burner_prototype.fuel_categories` is a dict of category name to true, so only the keys matter. The accepted fuel items come from `prototypes.get_item_filtered`, one `{filter = "fuel-category", ["fuel-category"] = name}` filter per category, combined with the default mode "or" (the owner pasted the `ItemPrototypeFilter` page). `LuaItemPrototype` has `fuel_categories` (plural) since 2.1, which the code does not read. A machine with neither source (heat, fluid) is refused with `error-unsupported-energy`; a fuel set in `config` that does not match the machine (a fuel on an electric machine, none on a burner machine, or one the machine cannot burn) is refused with `error-fuel-mismatch`. Picking a fuel by itself is deferred: a category such as "chemical" matches several items (wood, coal, solid fuel). Unsupported machine sizes are still refused. The generator copies this into `bpgen.EnergySource` and `GameData.fuels` (a set of item names); the planner and layout do not see it.
- What the assistant flagged about the owner's design (2026-11-01). (a) An inserter drops on the FAR lane of a belt only (or the right-hand lane when the belt points at it), so output inserters on one side can never fill both output lanes: the product gets one lane and the output is capped at 450 a minute (Secondary: forum posts quoting the wiki, https://forums.factorio.com/viewtopic.php?p=444098). (b) The priority list puts fewer machines (2) above a shorter column (3), but `size - 1` inserters can need MORE machines than `size` inserters with pole rows: gears at 60 a minute need 2 machines with 2 inserters a side and 1 with 3; at 180 a minute, 4 and 3. Both layouts are in the code (the pole-row one is unreachable from the generator now). A planner that built both and picked by the priority list would follow the list literally; not built, because the owner chose `size - 1`.
- Chains (owner, 2026-11-05; built 2026-11-06). Every blueprint is "ores in, final product out", so an item whose recipe needs a made ingredient gets one column per step, left to right, and the output belt of a column is the input belt of the next. The owner's answers: the steps are DERIVED from the game's recipes (not nested in the config); a recipe with more than one made ingredient (a tree) is REFUSED with a message; everything arrives as ONE combined patch (code and notes together; the standing rule is separate patches). How it works: `config.products` is only the set of requestable items. For an item the generator asks `prototypes.get_recipe_filtered` for the recipes that make it (`has-product-item` with a name filter), keeps those whose `categories` include a category named in `config.machines` (the first such category picks the machine), and `chain.resolve` follows the one made ingredient back until every ingredient is raw. Raw means no buildable recipe makes it (ores, stone); several buildable recipes for one item are refused as ambiguous (`error-ambiguous-recipe`); no recipe for the requested item is `error-no-recipe` (it replaces `error-missing-prototype` for that case). The tension with the owner's deferral of machine choice (2026-11-03, "defer which machine we'll pick as I'll request a whole technology research feature later"): recipes and raw items are read from the game, but the machine and fuel stay hardcoded, now per recipe category, so the research feature has one place to replace. Limits, all explained to the owner: (a) the belt between two columns is a PLAIN belt, so the intermediate product rides on ONE lane (450 a minute) and limits the next column: gears dropped from 403.2 to 225 a minute (one lane holds 450 plates, 450 / 100.8 = 4.46 assemblers' worth, so 5 assemblers are allowed and the lane is the limit; owner decision 2026-11-06 22:07: the hard limit follows the lanes, not whole machines. Before that it was 4 assemblers and 201.6); (b) each column must make what the next one NEEDS for the rate asked (owner, 2026-11-06 22:49: it used to make what all the machines of the next could eat, so 1 gear a minute built 6 furnaces; now `machines_for` walks back from the rate, multiplying by eats/makes of each stage, so it builds 1; the last stage's plan shows what it really makes and eats, e.g. 9.375 gears from 18.75 plates, and an earlier stage shows what its machines can make), and the planner takes the lowest limit over all columns (`plan_chain`: every belt limit is a fractional `machines_worth`; the maximum rate is `final_output(last)`, machines are `ceil(worth)`, an earlier stage is sized by what the next eats, capped at the belts); (c) only the LAST column's output belt may wind: a column that feeds another stays plain (`feeds_next` in the layout, `winds` in the planner) so the next column's inserters pick from a simple belt; (d) only the FIRST step may burn fuel (the fuel rides on the raw belt), so a burner machine in a later step is refused with `error-chain-fuel`; (e) every later step has exactly one ingredient, the previous product, else `error-chain-too-complex`; (f) a recipe with a fluid ingredient is `error-unsupported-recipe`; (g) the belt between two columns runs NORTH when the first column is the longer of the two for the work they do (fractional machines' worth x rows per machine), and SOUTH otherwise, whatever the rate (owner rule, 2026-11-06 22:59) (the owner's rule from his hand-built version, 2026-11-06; the first delivered patch always ran it south, which was wrong: see "Belt flow" under Chains). The player message lists the steps (`generated-first-stage`, `generated-next-stage`) inside `generated` / `generated-one-item`, whose numbering changed; the blueprint description lists the machines of every step.
- Machine size is read from `tile_width` and `tile_height`; only square 2x2 and 3x3 machines are laid out, anything else is refused (`error-unsupported-machine`).
- Pure modules (`planner`, `layout`, `config`) may read the constant table `defines` but never `game`, `prototypes`, `storage` or `script`.

## Layout (scripts/layout.lua)

One column of furnaces, items flowing south. Columns by tile x: 0 input belt, 1 input inserters, 2 and 3 furnace (2x2, top-left tile x = 2), 4 output inserters, 5 output belt. Furnace `i` (from 0) covers tile rows `2i` and `2i + 1`; the inserters sit in its top row (tile row `2i`). In the finished blueprint the furnace's centre position is (3, 2i + 1) and a belt on tile (0, 0) is at position (0.5, 0.5); `grid.position` does that conversion. Poles sit in the free bottom-row tiles of columns 1 and 4, for every second furnace, and are wired one after another down each side with one cross-link at the top. The output belt is `2N` tiles long (it keeps the full height so plates can carry on downstream). The input belt is `2N - 1` tiles: it stops at the last input inserter, in the top row of the last furnace (owner request 2026-10-29: no dangling tile past it). So a blueprint of N furnaces holds exactly `7N - 1 + 2 * ceil(N / 2)` entities: `4N - 1` belts, `N` furnaces, `2N` inserters and the poles. Checked against the previous layout for N = 1 to 60: the only difference is that one input belt tile. Numbers behind it: a furnace makes 18.75 plates/min (3.2 s recipe, speed 1); a standard belt lane carries 450/min (computed at runtime from the belt's speed).

Machine sizes 2 and 3 (2026-10-31). The shape is `{machine_size, input_inserters, output_inserters}`. Columns: 0 input belt, 1 input inserters, `2..1+size` machine, `2+size` output inserters, `3+size` output belt. Two pole modes, chosen by `max(inserters) >= size`. The generator only ever reaches the first (from 2026-11-01 it asks for at most `size - 1` inserters per side):
- Free-tile poles (the furnace case, and a 3x3 with fewer than 3 inserters on each side): inserters fill the top rows of each machine, poles sit in a free tile of columns 1 and `2+size` for every second machine, as before. The furnace layout is unchanged (compared for 1 to 60 furnaces).
- Pole rows (a side has as many inserters as the machine has rows, so no tile is free): machines are `size + 1` rows apart, starting at row 1. Row 0, the rows between machines and the row below the last hold a pole in each inserter column; poles are wired down each column and cross-linked at the top. Belts start at row 1 (the first machine's top). For 3x3 with 3 and 2 inserters, machine `i` covers rows `1 + 4i` to `3 + 4i`, centre (3.5, 2.5 + 4i).
The generic validator confirms power coverage and connectivity for 1 to 24 machines in the spec loops. A throwaway sweep (not in the repo) ran 1 to 60 machines for the five shapes the generator can now produce (2x2 with 1+1; 3x3 with 1 or 2 in and 1 or 2 out): no problems at the small pole's 2.5 supply radius and 7.5 wire reach, and they still pass down to a supply radius above 1.5 and a wire reach of 6 (3x3) or 4 (2x2), so there is about 1 tile of margin on the supply area and 1.5 on the wire. The layout does not read those two numbers from the game. Never checked in game.

Chains (2026-11-06). `layout.build_chain(stages, names)` takes a list of `{machine_count, machine, shape}` and lays the columns out left to right. Each column uses the columns of the single layout counted from its own input belt column (its `origin`): input inserters `origin + 1`, machine from `origin + 2`, output inserters `origin + 2 + size`, output belt `origin + 3 + size` (`origin + 4 + size` for the outer belt of a winding one, last column only). The next column's origin is the previous column's output belt column, so that belt is shared: the previous column draws it, from the first row down to the lower of (the previous column's last output inserter row, the next column's last input inserter row), with no tail below it (owner, 2026-11-06 23:17: the furnaces' second row used to carry a tile nothing used; the plain output belt of a SINGLE column still keeps the full height of its machines), and the next column draws no input belt. Columns may differ in machine count, size and inserter counts. All the columns of a chain start on the same row: row 0, or row 1 when ANY column has pole rows (they need a pole row above their first machine; `chain_first_row`), so a column without pole rows moves down one row beside one with them. The shared belt runs north when the previous column is the longer of the two for the work it does, else south (`share_belt`: `load` x `spacing` of each column, where `load` is the fractional number of machines' worth of work the rate asks, `Plan.load` from the planner; equal lengths run north). Owner rule, 2026-11-06 22:59: the direction must not change with the rate (the row rule ran 1 copper cable a minute south and 900 north). Consequence: the row guarantee (every output inserter has an input inserter ahead of it and the reverse) holds for a rate-matched chain but not for every pair of machine counts; checked over rates for the real chains (furnace to gear, furnace to cable, and a slow recipe) and for a furnace column feeding each of the five assembler shapes at 20 to 300 items a minute. (At 0.5 to 9 gears a minute, 1 furnace and 1 assembler, the assembler's second input inserter used to get no plates; since the inserters follow the share of work, 2026-11-06 23:09, that assembler has one input inserter and the problem is gone: the probe over all rates finds no flow problem in the gear, cable and slow chains.) A column of assemblers feeding another of similar length for its work is NOT covered and can leave inserters without plates; look at it when such a chain is added. (Before 2026-11-06 22:59 it compared the rows of the last inserters, north when the first column's was below the next one's.) A column's own input belt and the last column's output belt always run south. One copper wire joins the first output pole of a column to the first input pole of the next. Example, 2x2 furnaces then 3x3 assemblers: raw belt x = 0, inserters 1, furnaces 2-3, output inserters 4, plate belt 5, inserters 6, assemblers 7-9, output inserters 10, output belt 11 (and 12 when it winds). Checked: a single column is byte for byte the same as before (319,170 lines); a throwaway sweep ran every pair of the 13 shapes with 1 to 9 machines each (13,689 chains) and 432 three-column chains through the generic validator: no problems. The validator does not check belt paths, so the shared belt's rows were checked by specs (no gap, down to the last inserter either column needs), and its direction by `plate_flow_problems` (see "Belt flow").

Belt flow (2026-11-06). Found after the first chain patch was delivered, when the owner described the same problem from his hand-built version: an item only travels the way its belt runs, so an inserter picks up the plates dropped in its own row or earlier along the belt, and no others. The delivered layout always ran the plate belt south, but for 100 gears a minute the furnace column (11 furnaces, rows 0 to 21) is much longer than the assembler column (inserters in rows 0 to 4), so the plates of the 8 lowest furnaces flowed south past every assembler and piled up on the dead end below the last inserter. A steady-state model of the belt (a furnace makes 18.75 plates a minute, an inserter moves 50.4, a lane holds 450, a plate dropped in a row can be picked in that row) gave 28% of the 100 gears a minute asked for; over the whole range of 1 to 201 gears a minute 192 of the 201 whole rates fell short, the worst at 19% (50 gears a minute). With the rule above (north when the first column reaches further down, columns starting on the same row) it gives 100% at every whole rate from 1 to 201. The earlier note that the belt "should fill all the way up" was wrong: nothing carries plates back up. What the rule guarantees, and nothing more: every output inserter has an input inserter ahead of it on the belt and every input inserter has an output inserter before it (`plate_flow_problems` in `spec/layout_spec.lua`, run for 25 pairings of column shapes by 4 pairs of machine counts; a throwaway sweep of 4,900 chains, 1 to 14 machines per column, found no failure, while the same rule without the shared start row failed in 628 of 3,600 chains of 1 to 12 machines per column, all with pole rows). It does NOT even out the load: the inserters nearest the start of the belt have the first pick, so a machine at the end of the flow can get less than its share when the two columns are about equally long (the owner's "some machines more starved, others overfed"). The planner does not know this; it sizes every column by totals. Equal reach goes south by convention; north would work as well (three equivalent surviving mutants).

Winding between steps (2026-11-06, open). The owner suggested allowing the winding output belt between chain steps too, once the positions are right, and will check in game. Not built. What to know first: (1) the winding belt exists only for a 3x3 machine with two output inserters, so it does not apply to a furnace column (2x2, one output inserter), and the gear chain's plate lane limit (gears 201.6 a minute) would not change; two lanes from 2x2 machines need a new pattern (the "alternating the inserter rows" follow-up above); (2) the winding belt as built runs south, so between steps it needs a north-running mirror for a first column that is longer; (3) "only the last column winds" is a cautious choice of this iteration, so that the next column picks from a plain belt, not a limit of Factorio. Built for furnaces built wide only (2026-11-12, 5u): the paired winding belt of 5n and 5o runs between columns for 2x2 machines with one output inserter each, a north-running one is the south one reflected (`Builder:add_winding_tile`, with its first tile a row past the last one), and the next column's inserters pick from the outer column. Every other machine still keeps a plain belt between columns.

## Passing state around (owner, 2026-11-03/04)

The owner noticed how many values and types are passed between functions. Agreed direction: a "partitioned blackboard" - bundle the values that always travel together, one bundle per level, and keep the modules separate (generator reads `prototypes`, planner and layout stay pure and are tested with only the values each test names). A single object shared by generator and layout was considered and not chosen: it would blur the one module that touches `prototypes`, make every test build a large object, and hide who reads or writes which field. Order of work: (1) the layout builder, done 2026-11-04; (2) the generator "Job", done 2026-11-04 (see below); (3) a "what one machine does" record in the planner, done 2026-11-04 (see below). Not hardcoding machines is a standing principle: machine facts come from the game; only layout assumptions are hardcoded, each named and refused when violated.

Checked by a throwaway script that dumps `layout.build` for 1 to 60 machines in all 13 shapes (machine size 2 and 3, every inserter count per side up to the size): the dump of 319,170 lines is byte for byte the same before and after, and three deliberate breakages were each detected by it. ## Tile coordinates (owner request 2026-10-27)

Layout code and tests think in tiles, not centres, so there are no `+ 0.5` fudges outside `scripts/grid.lua`. Convention for EVERY entity size: the position written in code is the top-left tile the entity covers; y grows downward; `grid.position` adds half the entity's width and height to get the centre. A furnace at tile (2, 0) is at position (3, 1). `spec/support/builders.lua` (`belt`, `furnace`, `inserter`, `pole`) take tile coordinates, and fractions build deliberately misaligned entities (`inserter(0.75, 0, ...)`). Possible later issue: an entity rotated a quarter turn swaps its width and height; today every entity is square, so nothing handles that yet. Checked: layout output for 1 to 60 furnaces is identical to before the change.
