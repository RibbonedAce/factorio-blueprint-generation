# Project status

Last updated: 2026-11-01

## Goal

A Factorio 2.1 mod where the player gives only an item to produce and a rate of output, and gets a pastable blueprint that carries raw materials (ores and so on) to machines (furnaces, assemblers) to produce the final product.

## What exists

- `info.json`, `LICENSE`, `.gitignore`, and the shortcut icons in `graphics/` (the owner will replace the icons later; `data.lua` assumes the same file names, `icon_size = 56`, `small_icon_size = 24`).
- `data.lua`: the shortcut prototype `blueprint-generation-open` (`action = "lua"`).
- `control.lua`: events and GUI only. Shortcut opens or closes a window (item picker filtered to supported products and starting on `config.default_product`, iron plate (owner request 2026-10-29; set with `item_button.elem_value` after `add`, NOT verified in game, and `elem_value` as an `add` field is not in the API notes), rate field in items per minute, Close and Generate buttons). Generate calls `generator.generate`, then puts the blueprint on the cursor. The GUI is stateless (values are read from the window's elements by name), so there is no `storage`.
- `scripts/config.lua`: every hardcoded choice (first-tier belt, inserter and pole names; supported products and their recipe, machine and fuel). Numbers that the game already knows about those entities are NOT stored here (see Decisions).
- `scripts/planner.lua`: pure maths (small private helpers for each step, and `plan` is an outline of them). `planner.plan(request)` takes ONE table (`bpgen.PlanRequest`: product, rate, recipe, machine speed, lane capacity, optional fuel, optional inserter limits) instead of seven positional arguments, two of them plain numbers side by side that are easy to swap. It decides the machine count (float-safe rounding), how the input items sit on the two belt lanes, the inserters per side and, when inserters limit a machine, how much slower it runs. Also `lane_items_per_minute(belt_speed)` and `inserter_items_per_minute(rotation_speed)`.
- `scripts/layout.lua`: pure, machine count in, blueprint entities out (see "Layout" below). Written in tile coordinates. Since 2026-11-04 the steps share one `Builder` table (entities, geometry, names, machine count, poles) and are its methods; see "Passing state around" below.
- `scripts/grid.lua`: pure, converts between a TILE (the top-left tile an entity covers, whole numbers, y grows down) and a POSITION (the entity's centre, which Factorio blueprints use): `grid.position(tile_x, tile_y, width, height)` and `grid.top_left_tile(position, width, height)`; sizes default to 1x1. The only place the "+ half the size" lives (owner request 2026-10-27). The validator deliberately does NOT use it, so a mistake in `grid` cannot hide behind the same mistake in the checker.
- `scripts/generator.lua`: the only module that reads `prototypes` (recipe, machine speed and size, belt speed, inserter rotation speed); builds plain tables and numbers for the planner and layout, and the messages (which item goes on which lane comes from the plan).
- `locale/en/blueprint-generation.cfg`: all texts in a `[blueprint-generation]` section.
- `spec/`: the test suite, run with busted outside the game (see "Testing"). `<thing>_spec.lua` files hold the tests; `helper.lua` (fake `defines`, loads the custom assertions), `support/assertions.lua` (custom luassert assertion), `support/builders.lua` (setup helpers) are the toolkit. `.busted` in the repo root is busted's config.
- `spec/support/blueprint_validator.lua`: layout-independent sanity checks for any list of blueprint entities (see "Testing"). Test tooling only; the game never loads it.

## Decisions

- The mod is Lua, written from scratch on `llm-main`. `.agents/` is tracked in git.
- Input is a GUI opened from a shortcut-bar button. Output is a blueprint on the cursor.
- "Resource" means the ITEM TO PRODUCE (for example iron plate). The rate is in items per minute (assumption, confirm with the owner).
- Input belt lanes (owner, 2026-11-01): the input belt has two lanes, and what goes on it is the recipe's ingredients plus the fuel, if the machine burns one. One item fills both lanes; two items get a lane each (an ingredient and a fuel, or two ingredients); more are refused as `unsupported-recipe`. The player decides which lane holds which item (the message names the items). The product always rides on ONE lane of the output belt. A recipe must make exactly one product, or the extra product would clog the machine.
- One column only: a rate that needs more machines than the belt lanes can serve (24 furnaces, 450 plates a minute, for plates) is refused with a message that names the maximum, instead of building several columns. Several columns is a candidate later iteration.
- Inserters are the electric `inserter`, and the blueprint INCLUDES `small-electric-pole`s with copper wires between them; the player connects the poles to their grid. History: the owner first answered "no poles" (2026-10-25), then changed their mind later that day and asked for the poles to be coded in. Burner inserters were rejected (their output side would run out of fuel).
- Numbers that belong to a hardcoded entity are read from the game at runtime instead of stored in `config` (owner, 2026-10-26). Done so far: the belt lane capacity, computed from the belt's `belt_speed` (`speed x 4 items per lane per tile x 60 ticks x 60 seconds`; 450 per minute for the standard belt), alongside the furnace crafting speed and the recipe that were already read. Candidates for later, not done yet: the pole's supply area and wire reach (the layout still assumes 2.5 and 4 tiles), the furnace's size (`tile_width`, `tile_height`; the layout assumes 2x2), and the inserters' pickup and drop positions (which would also settle the direction question).
- Testing scaffolding (owner, 2026-10-26): build generic test tooling now, but do NOT build a general production-chain model yet; generalize from the second or third real example (steel plate is the first true chain). Unit tests use made-up numbers on purpose, so they hold whatever the game numbers are; no fixtures from real `data.raw`. The blueprint validator deliberately does NOT check belt paths (later layouts may bend belts to save space) or item flow (a game-specific quirk).
- Lanes and inserters (owner, 2026-11-01). The owner's requirements, in priority order: (1) poles reach everything that needs power; (2) minimize the number of machines; (3) minimize the length of the machine column (do not space the machines out); (4) maximize the rate one blueprint allows. Given only basic poles and no underground belts, splitters or long inserters, the owner's solution is: two lanes for the input items (see "Input belt lanes"), one product, and up to `size - 1` inserters on each side of a machine (`layout.max_input_inserters`: 1 for a 2x2, 2 for a 3x3), which leaves one tile beside every machine free for a pole. History: on 2026-10-31 the owner chose several inserters per machine (3 in, 2 out for gears, with pole rows; confirmed working in game on 2026-11-01); an intermediate "one inserter per side" version was offered and replaced by this design the same day.
- How the planner uses the inserter limit: each side gets as many inserters as the machine needs, up to the limit. When the limit is below what a machine could use at full speed, the machine runs slower (every flow shrinks by `max inserters on the busiest side x inserter items a minute / busiest side`) and everything is sized for that: with two basic inserters (50.4 items a minute each) a gear machine can take 100.8 of the 120 plates it could eat, so it makes 50.4 gears, not 60. Resulting numbers (belt lane 450): gears need 2 input and 1 output inserter per machine, at most 8 machines, 403.2 gears a minute; furnaces are unchanged. `inserter_items_per_minute(rotation_speed)` is `rotation_speed x 60 x 60`; it ignores stack bonuses and belt movement.
- Winding output belt (owner, 2026-11-02): two output inserters can fill both output lanes if the output belt is 2 tiles from the machine side and follows `DDLDRDDLDR...`: inserter A is left of the `D` between `L` and `R` (drops on the far, east lane), inserter B is left of the next `D`, dropping onto an `R` stub that side-loads the inner (west) lane of the main belt. Output inserter limit is `min(2, size - 1)` (`layout.max_output_inserters`); the input limit stays `size - 1` (`layout.max_input_inserters`); both replaced `max_inserters_per_side`. Built only for a 3x3 machine with exactly 2 output inserters in packed (free-tile pole) mode (`winds_output` in `layout.lua`); the belt then needs one more column (inner column `3+size`, outer `4+size`) and six tiles per machine. A single output inserter keeps the straight belt, so gears (1 output inserter) still use one lane; alternating the inserter rows is an optional follow-up. The planner's per-lane rule with 2 output inserters is CONSERVATIVE and UNVERIFIED in game: machines <= floor(lane / inserter items a minute), because the first inserter takes all it can. Example: a doubling recipe (1 plate -> 2 items, 0.5 s, speed 0.5) allows 806.4 a minute instead of 403.2. The validator does not check belt paths; a throwaway trace script confirmed the path and one side-load per machine.
- Energy source of a machine (owner, 2026-11-03). Machine facts are read from the game, not hardcoded; which machine makes an item stays in `config.products` until the owner's research feature (not decided). The generator reads the machine prototype: `electric_energy_source_prototype` present means electric, `burner_prototype` present means burner (the two are mutually exclusive, and each is nil when the machine does not use it); `burner_prototype.fuel_categories` is a dict of category name to true, so only the keys matter. The accepted fuel items come from `prototypes.get_item_filtered`, one `{filter = "fuel-category", ["fuel-category"] = name}` filter per category, combined with the default mode "or" (the owner pasted the `ItemPrototypeFilter` page). `LuaItemPrototype` has `fuel_categories` (plural) since 2.1, which the code does not read. A machine with neither source (heat, fluid) is refused with `error-unsupported-energy`; a fuel set in `config` that does not match the machine (a fuel on an electric machine, none on a burner machine, or one the machine cannot burn) is refused with `error-fuel-mismatch`. Picking a fuel by itself is deferred: a category such as "chemical" matches several items (wood, coal, solid fuel). Unsupported machine sizes are still refused. The generator copies this into `bpgen.EnergySource` and `GameData.fuels` (a set of item names); the planner and layout do not see it.
- What the assistant flagged about the owner's design (2026-11-01). (a) An inserter drops on the FAR lane of a belt only (or the right-hand lane when the belt points at it), so output inserters on one side can never fill both output lanes: the product gets one lane and the output is capped at 450 a minute (Secondary: forum posts quoting the wiki, https://forums.factorio.com/viewtopic.php?p=444098). (b) The priority list puts fewer machines (2) above a shorter column (3), but `size - 1` inserters can need MORE machines than `size` inserters with pole rows: gears at 60 a minute need 2 machines with 2 inserters a side and 1 with 3; at 180 a minute, 4 and 3. Both layouts are in the code (the pole-row one is unreachable from the generator now). A planner that built both and picked by the priority list would follow the list literally; not built, because the owner chose `size - 1`.
- Machine size is read from `tile_width` and `tile_height`; only square 2x2 and 3x3 machines are laid out, anything else is refused (`error-unsupported-machine`).
- Pure modules (`planner`, `layout`, `config`) may read the constant table `defines` but never `game`, `prototypes`, `storage` or `script`.

## Layout (scripts/layout.lua)

One column of furnaces, items flowing south. Columns by tile x: 0 input belt, 1 input inserters, 2 and 3 furnace (2x2, top-left tile x = 2), 4 output inserters, 5 output belt. Furnace `i` (from 0) covers tile rows `2i` and `2i + 1`; the inserters sit in its top row (tile row `2i`). In the finished blueprint the furnace's centre position is (3, 2i + 1) and a belt on tile (0, 0) is at position (0.5, 0.5); `grid.position` does that conversion. Poles sit in the free bottom-row tiles of columns 1 and 4, for every second furnace, and are wired one after another down each side with one cross-link at the top. The output belt is `2N` tiles long (it keeps the full height so plates can carry on downstream). The input belt is `2N - 1` tiles: it stops at the last input inserter, in the top row of the last furnace (owner request 2026-10-29: no dangling tile past it). So a blueprint of N furnaces holds exactly `7N - 1 + 2 * ceil(N / 2)` entities: `4N - 1` belts, `N` furnaces, `2N` inserters and the poles. Checked against the previous layout for N = 1 to 60: the only difference is that one input belt tile. Numbers behind it: a furnace makes 18.75 plates/min (3.2 s recipe, speed 1); a standard belt lane carries 450/min (computed at runtime from the belt's speed).

Machine sizes 2 and 3 (2026-10-31). The shape is `{machine_size, input_inserters, output_inserters}`. Columns: 0 input belt, 1 input inserters, `2..1+size` machine, `2+size` output inserters, `3+size` output belt. Two pole modes, chosen by `max(inserters) >= size`. The generator only ever reaches the first (from 2026-11-01 it asks for at most `size - 1` inserters per side):
- Free-tile poles (the furnace case, and a 3x3 with fewer than 3 inserters on each side): inserters fill the top rows of each machine, poles sit in a free tile of columns 1 and `2+size` for every second machine, as before. The furnace layout is unchanged (compared for 1 to 60 furnaces).
- Pole rows (a side has as many inserters as the machine has rows, so no tile is free): machines are `size + 1` rows apart, starting at row 1. Row 0, the rows between machines and the row below the last hold a pole in each inserter column; poles are wired down each column and cross-linked at the top. Belts start at row 1 (the first machine's top). For 3x3 with 3 and 2 inserters, machine `i` covers rows `1 + 4i` to `3 + 4i`, centre (3.5, 2.5 + 4i).
The generic validator confirms power coverage and connectivity for 1 to 24 machines in the spec loops. A throwaway sweep (not in the repo) ran 1 to 60 machines for the five shapes the generator can now produce (2x2 with 1+1; 3x3 with 1 or 2 in and 1 or 2 out): no problems at the small pole's 2.5 supply radius and 7.5 wire reach, and they still pass down to a supply radius above 1.5 and a wire reach of 6 (3x3) or 4 (2x2), so there is about 1 tile of margin on the supply area and 1.5 on the wire. The layout does not read those two numbers from the game. Never checked in game.

## Passing state around (owner, 2026-11-03/04)

The owner noticed how many values and types are passed between functions. Agreed direction: a "partitioned blackboard" - bundle the values that always travel together, one bundle per level, and keep the modules separate (generator reads `prototypes`, planner and layout stay pure and are tested with only the values each test names). A single object shared by generator and layout was considered and not chosen: it would blur the one module that touches `prototypes`, make every test build a large object, and hide who reads or writes which field. Order of work: (1) the layout builder, done 2026-11-04; (2) the generator "Job", done 2026-11-04 (see below); (3) a "what one machine does" record in the planner, done 2026-11-04 (see below). Not hardcoding machines is a standing principle: machine facts come from the game; only layout assumptions are hardcoded, each named and refused when violated.

Layout builder (2026-11-04): `Builder` in `layout.lua` holds `entities`, `geometry`, `names`, `machine_count` and `poles` as fields. `add`, `connect`, `machine_top`, `add_belt`, `add_belt_column`, `add_winding_output_belt`, `add_belts`, `add_inserters`, `add_pole_pair`, `add_machine_row`, `add_pole_rows`, `add_machines` and `wire_poles` are methods; the most parameters any of them takes is three (it was six). `Builder.__index = Builder` is how Lua finds the methods on a builder; the builder lives for one `layout.build` call and is never stored in `storage`, so it needs no metatable registration. The `bpgen.Blueprint` class (closures `add` and `connect`) is gone. Checked by a throwaway script that dumps `layout.build` for 1 to 60 machines in all 13 shapes (machine size 2 and 3, every inserter count per side up to the size): the dump of 319,170 lines is byte for byte the same before and after, and three deliberate breakages were each detected by it. Longest method 14 lines; `geometry_of` is unchanged (16 lines, complexity 7).

Generator job (2026-11-04): `bpgen.Job` holds `item_name`, `rate_per_minute`, `product`, `names` and `game` (the `GameData`), built once by `read_job` (which also refuses an unsupported item or a missing prototype) and never changed. `machine_problem`, `make_plan`, `describe_blueprint`, `success_message` and `assemble` take the job (and the plan, for the last three) instead of four to six loose values: no function takes more than two parameters now (it was up to six). Deliberate difference from the first sketch: the plan is passed as a second argument, not added to the job as an optional field, because every step after planning then has a plan that is certainly there, with no nil checks, and the job stays one table that is complete when it is made. `machine_size_of(job)` is the one place that casts the machine size to a number, because `machine_problem` has already refused a machine without one. `generator.generate` is 18 lines. Checked by a throwaway script that dumps `generator.generate` over 19 scenarios (each recipe shape, other belt, furnace and inserter speeds, 2x2 and 4x4 and non-square machines, a burner assembler, a heat machine, fuel mismatches, a missing recipe and building, an unsupported item) at 18 rates each, 342 results and 8,090 lines: byte for byte the same before and after, and four deliberate breakages (the rate, the fuel, the machine size and the machine name in the description) were each detected by it.

Planner machine rates (2026-11-04): `rates_per_machine(request)` returns one `bpgen.MachineRates` table: `output`, `inputs` (per ingredient, in the recipe's order), `input_inserters` and `output_inserters`, all for ONE machine after the inserter slowdown. `machines_per_belt(request, lanes, per_machine)` and `output_machine_limit(request, per_machine)` take it instead of loose numbers (they took four values each), and the inserter counts are worked out once, inside `rates_per_machine`, where they used to be worked out twice (once for the belt limit, once for the plan). The values are all computed from the recipe, the machine speed and the game's inserter and belt numbers; nothing in it names a machine. `planner.plan` is 23 lines, complexity 4; the longest new function is `rates_per_machine` (20 lines, complexity 3). `inserters_needed` moved above `rates_per_machine` (helpers go above their callers). Checked by a throwaway script that dumps `planner.plan` over 127,680 requests (7 recipe shapes, 5 recipe times, 4 machine speeds, 4 lane sizes, with and without fuel, 6 inserter limit sets, 19 rates): byte for byte the same before and after, with 33,547 plans, 17,525 "rate too high" refusals and 76,608 unsupported recipes in it; six deliberate breakages (swapped inserter counts, the winding test on the wrong side, the slowdown left off the inputs or the output, the ingredient loop emptied, one lane for every ingredient) were each caught by both the dump and the busted suite.

## Tile coordinates (owner request 2026-10-27)

Layout code and tests think in tiles, not centres, so there are no `+ 0.5` fudges outside `scripts/grid.lua`. Convention for EVERY entity size: the position written in code is the top-left tile the entity covers; y grows downward; `grid.position` adds half the entity's width and height to get the centre. A furnace at tile (2, 0) is at position (3, 1). `spec/support/builders.lua` (`belt`, `furnace`, `inserter`, `pole`) take tile coordinates, and fractions build deliberately misaligned entities (`inserter(0.75, 0, ...)`). Possible later issue: an entity rotated a quarter turn swaps its width and height; today every entity is square, so nothing handles that yet. Checked: layout output for 1 to 60 furnaces is identical to before the change.

- `spec/support/blueprint_validator.lua` takes the entity list plus a catalog (name to kind, size, needs_power, supply_radius, wire_reach; numbers made up in the tests) and returns a list of problems. It checks: known entity names and unique numbers, grid alignment (odd sizes on half tiles, even on whole), no overlapping tiles, every inserter picks up from and drops onto a belt or machine with at least one end a machine, every entity that needs power is inside a pole supply area (footprint overlap), wires join two poles within the shorter reach using the copper connector and start on the entity that lists them, and all poles form one network. The layout-specific checks (counts, numbering, belts south, which inserter does what) stay in `check_layout`. The validator has its own tests (`spec/blueprint_validator_spec.lua`): tiny hand-built blueprints, each broken in one specific way, and each break must be reported; boundary cases (a pole exactly at the edge of its supply area, a wire exactly as long as the reach) are covered both ways. Mutation checks on the validator code (2026-10-26) first left three survivors (supply area ignoring entity size, an inserter allowed to pick up from anything, wire reach using the longer of two poles), each fixed with a new test; a fourth (supply area ignoring height) was found and fixed the same way. Two mutants fail by crashing rather than a clean failure (unknown names allowed; wire kinds unchecked); still detected.
- The validator shares the inserter-direction assumption with the layout (direction = side picked up from), so it cannot catch that assumption being wrong; only the in-game run can.
- An earlier note said `control.lua` was exercised against fake GUI, player and game objects in a scratch harness (29 checks). That harness is not in the repo and was not re-run this session; `control.lua` itself was not changed by the pole removal.
- What this proves: the logic is self-consistent and the code parses. What it does NOT prove: that Factorio accepts the blueprint, and anything about real item names, inserter orientation or wires. Only the owner's in-game run proves that.

## Unverified in iteration 2 (check on the first in-game run)

1. **Inserter orientation.** `layout.lua` sets `direction = west` on both inserters, assuming an inserter's direction is the side it PICKS UP from (so they move items east). If the inserters point the wrong way in game, swap to `east` in `layout.lua` (the layout test then needs the same change). Source: memory, not the JSON.
2. **Wire format.** Each wire is stored once, on the entity it starts from, as a four-entry list (this entity's number, connector, other entity's number, connector), using `defines.wire_connector_id.pole_copper`. The JSON describes a `BlueprintWire` as "a single wire" with a source and a target, which fits one entry per wire, but the docs do not say whether `wires` should list a wire on both ends. If the poles come out unconnected in game, try listing each wire on both poles.
3. **Entity names** `stone-furnace`, `transport-belt`, `inserter`, `small-electric-pole`, `coal`: standard base names from memory. The generator checks the entities exist and reports a message if not.
4. **Small pole range.** Spacing assumes a supply area reaching 2.5 tiles and wire reach of at least 4 tiles (the farthest wire is 4 tiles). The runtime can report real values (`get_supply_area_distance`, `get_max_wire_distance` on the entity prototype); the layout does not read them yet.
5. **Runtime `belt_speed`.** The generator treats `prototypes.entity["transport-belt"].belt_speed` as the same raw value the prototype docs call `speed` (0.03125 for the standard belt). The runtime docs say only "the speed of this transport belt". To check in game: ask for a rate above the limit (for example 1000 per minute); the message must say the maximum is 450 per minute. A different number means the unit differs.
6. **Dotted `require`** (`require("scripts.generator")`) is used for the first time. It follows the 2.0 wiki tutorial and passed under busted; confirm in 2.1.
7. **Item picker filter** (`elem_filters` by name) is verified against the JSON but untested in game.
8. **Temporary cursor blueprint** (owner request 2026-10-29: the blueprint must not take an inventory slot). `control.lua` sets `player.cursor_stack_temporary = true` after `set_stack("blueprint")`. The attribute exists (read/write boolean, see `research/api-reference-2.1.23.md`), but WHEN to set it (before or after `set_stack`), and whether pasting works with it, are untested in 2.1: a 1.1.74 forum report says paste wrongly reported a pasted blueprint as not temporary (fixed by staff the next release). If the blueprint still lands in the inventory, try setting the flag before `set_stack`, or ask the owner to attach `runtime-api.json` so the docs text for the attribute can be read.
9. Whether `set_blueprint_entities` repositions entities (the `fix_positions` default is not documented); the layout keeps entities on valid tile positions either way.

## Unverified in the iron gear iteration

The code reads it as turns per tick (0.014 x 3600 = 50.4 items a minute, which matches the basic inserter's known 0.83 swings a second, from memory). 3. **Pole rows layout** is unreachable from the generator since 2026-11-01; only the layout specs exercise it. It was confirmed in game with the first gear version.
4. **Two inserters in one column beside a 3x3 machine** (tile rows 0 and 1, with the pole in row 2) are assumed to work like the three the owner ran.
5. **Plates on both input lanes.** The generator relies on inserters taking from either lane of a belt (the gear wheel puts the same item on both). Not verified; the owner was offered the chance to paste the wiki text about which lane an inserter picks up from.
6. **One lane for the product.** An inserter drops on the far lane of a belt (right-hand lane when the belt points at it). Secondary source only: forum posts quoting the wiki.
7. **Two-ingredient recipes.** The planner and generator support them (one lane per ingredient, the flows added up for the inserters), but no product in `config.products` uses one, so only unit specs cover them (made-up recipes under the `iron-gear-wheel` label). Never run in game.
8. **Fluids are not handled.** `read_recipe` copies every ingredient as an item, so a recipe with a fluid ingredient would stop `success_message` with a script error (there is no item prototype for it). Not handled because no configured recipe has one; refuse such recipes before adding one.

## Risks and flags

- **Icon files.** The owner is replacing them; sizes assumed as above.
- **Folder name.** The game only loads a mod folder named `blueprint-generation` or `blueprint-generation_0.0.1` (see `research/mod-structure.md`).
- **Lua environment.** Modified Lua 5.2.1 (not 5.1, and not the 5.3 of `texlua`): no `io`, `os`, `coroutine`; `require` only at file top level. Avoid 5.3-only syntax (`//`, bitwise operators, `utf8`, `math.type`), and format numbers with `string.format`, because 5.3 prints `3.0` where 5.2 prints `3`.
- **Load sequence and desync rules.** See `research/data-lifecycle.md` and `research/modding-tutorial.md`.
